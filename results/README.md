# Сдача результатов CQA

Формат JSON 1.0 из приложения к гайду организаторов. Команда: **DCI_Hack_kiker**.

До стоп-кода в открытом Git-репозитории должны находиться:

- `results/dev/results.json` — 65 DEV-диалогов: 60 чатов и 5 голосовых транскриптов.
- `results/prod/results.json` — ровно 10 контрольных чатов FBroker, включая явные ошибки обработки.

SWAP сохраняется отдельно в приватных исходных данных. Сейчас он не оценивается и в `results/prod` не добавляется. Commit без push и локальное сохранение не выполняют требование сдачи.

## Экспорт реальных оценок

Запускайте из корня проекта. Пути `data/control/*` ниже — пример расположения приватных входов; подставьте фактические файлы своего запуска.

```sh
python3 scripts/export_submission.py \
  --source data/control/fbroker.json \
  --predictions data/control/predictions.json \
  --checklist data/control/checklist.json \
  --team-name DCI_Hack_kiker \
  --model-mode local \
  --count 10 \
  --output results/prod/results.json
```

`--source` — исходный ответ API или массив исходных диалогов. `--predictions` — сохранённые реальные оценки приложения. `--checklist` — точный снимок чек-листа этого запуска, включая его метаданные: проверяются хеши, поэтому другой файл с похожим содержимым не подходит.

Имя модели определяется по реальным метаданным оценок. `local` обозначает самостоятельно запущенную модель, например Qwen через Ollama на арендованном GPU; `external_api` — внешний AI API; `hybrid` — смешанный способ. Если все попытки завершились ошибкой, укажите `--model-name` с действительно использованной моделью. Для DEV используйте соответствующие исходные файлы, `--count 65` и `--output results/dev/results.json`.

## Проверка перед отправкой

```sh
python3 scripts/export_submission.py \
  --source data/control/fbroker.json \
  --validate results/prod/results.json \
  --count 10
```

Экспортёр проверяет:

- совпадение исходных ID, отсутствие повторов и чужих записей;
- хеши диалога и чек-листа, наличие фактической модели и точность цитат;
- ровно восемь критериев, их официальные коды и JSON-типы;
- `evidence_turns` с 1 по полному исходному массиву, включая клиента, бота и системные события;
- итог по применимым весам с исключением N/A и округлением HALF_UP до двух знаков;
- совпадение `critical_flag` с критерием `critical`, без обнуления итогового балла.

Внутренние коды преобразуются в официальный формат: `needs → discovery`, `identity → identification`, `management → dialogue`, `closing → closure`, `gross_error → critical`. Остальные коды сохраняются. `yes/no/na` преобразуются в `true/false/null`, оценки шкал — в числа без изменения ступени.

Если оценка отсутствует или не прошла проверки, её ID сохраняется с `status: "error"`, `criteria: []`, `score: null` и причиной в `error`. Ошибки не заменяются нулевыми баллами. Такой файл создаётся, но команда завершится кодом 2. `--allow-errors` разрешает код 0 при осознанной сдаче неполного результата к дедлайну. Код 1 означает общую ошибку входных данных или формата.

После проверки отправьте оба файла через commit и push и убедитесь, что они доступны в репозитории. Исходные транскрипты, API-ключи и подписанные URL в публичный репозиторий не включаются.

Корректный формат и успешная обработка не доказывают точность AI относительно Ground Truth. Баллы в этих файлах оценивают операторов; официальная точность системы требует независимых эталонов.
