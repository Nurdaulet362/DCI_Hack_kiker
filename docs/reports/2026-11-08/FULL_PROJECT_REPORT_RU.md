# Полный отчёт о проекте DCI Hack kiker

Состояние на 8 ноября 2026 года • Для Нурдаулета и команды • Подготовлено Codex

Проект CQA — Conversation Quality Analytics — уже работает как локальное приложение для оценки клиентских диалогов Freedom Broker. Он загружает транскрипты, применяет редактируемый чек-лист, объясняет выводы цитатами, хранит историю и позволяет пересматривать оценки через апелляции. Главный достигнутый результат — два полных реальных прогона всех 65 DEV-диалогов и проверяемое сравнение результатов после доработки оценщика.

Качество модели улучшилось на части разобранных ошибок, но остаётся недостаточно надёжным для автоматического решения без проверяющего. Официального Ground Truth нет, поэтому процент точности и вероятность попадания в топ-50 пока неизвестны. Средний балл 89,97 относится к работе операторов и не является точностью AI.

| Что проверено | Текущее состояние |
|---|---|
| Данные | 65 диалогов, 8 критериев, 520 ответов в каждом полном прогоне |
| Последний реальный прогон | 65 из 65 приняты, 130 запросов, без ошибок формата и запросов |
| Модель | Qwen3:30b Q4_K_M через Ollama на арендованной RTX A6000 |
| Сайт | Результаты импортированы; прежние оценки сохранены в истории |
| Проверки программы | 72 автоматических теста прошли при последней доработке |
| GPU и бюджет | Обе машины удалены; расчёт двух аренд $1,5924 при лимите $5 |
| Главный пробел | Нет независимой полной разметки и измерения точности на новых данных |

Пользователь определял цель, ограничения, провайдеров и визуальные предпочтения. Codex реализовал приложение, провёл инженерные проверки, подготовил эксперименты и отчёты. Все интерпретации спорных диалогов в этом документе являются диагностикой ассистента; они не заменяют решения экспертов организаторов.

Этот отчёт объединяет разработку, архитектуру, результаты, ошибки и план продолжения. Отдельный документ «Отчёт о NVIDIA и Brev» раскрывает аренду, модель, расходы и порядок следующего запуска. Приложение в конце содержит баллы всех 65 диалогов до и после доработки.

## Задача хакатона

По предоставленным критериям главный ориентир — близость AI-оценок к эталонам организаторов на 10 ранее неизвестных транскриптах. Дополнительно оцениваются функциональность, удобство, реальный анализ новых диалогов и разнообразие архитектур. В предоставленном тексте числовые веса этих направлений не указаны. Наличие облачного и локального адаптеров само по себе не гарантирует конкурсных баллов.

## Что было сделано в ходе работы

Первым этапом создана основа приложения: импорт из API и JSON, нормализация сообщений, редактор чек-листа, расчёт баллов, SQLite, карточка диалога и API для интерфейса. Из API загружен DEV-набор из 65 транскриптов. Появились история оценок, версии правил, ссылки на доказательства и апелляции с сохранением исходного ответа AI.

Далее добавлены адаптеры OpenAI Responses, OpenAI-совместимого API и Ollama. Ранний облачный эксперимент не стал рабочим контуром: были зафиксированы таймауты, ошибки сервиса и невалидные доказательства, поэтому финальный запуск перенесён на NVIDIA/Brev с Ollama и Qwen3:30B. Запись модели в настройках сама по себе не означает работающую генерацию.

После просьбы пропустить первый диалог отдельно проверен p1-ru-002 — также таймаут около 180 секунд. Успешную оценку через предоставленные Grok-ключи по сохранённым протоколам подтвердить нельзя. Расходы этих прежних API-проб в расчёт Brev не входят; их счета не сверялись.

После аудитов доработаны надёжность и интерфейс. Задачи сохраняются в SQLite, прогресс переживает F5, перезапуск помечает незавершённые задачи прерванными. Повторный запуск использует снимки и сохраняет уже полученные результаты. Исправлена строгая валидация чек-листа, добавлено сохранение его черновика. Benchmark стал явно показывать пропуски, ошибки, покрытие и несовместимые результаты.

Интерфейс последовательно менялся по пожеланиям пользователя. Текущая палитра — небесно-голубой, белый и ярко-розовый. Рабочая область стала компактнее, подписи и реплики читаемее, для мобильного экрана добавлен переключатель диалога и оценки. Нулевая оценка, частичное выполнение и N/A отображаются по-разному. Появилась очередь ручной проверки.

Для разработки использовались ECC, локальная копия UI UX Pro Max и Graphify. ECC применялся для проверки безопасности и регрессий; рекомендации UI UX Pro Max — для рабочего экрана и навигации. Graphify построил карту 244 узлов и 696 связей, без найденных циклов импортов. Часть связей получена эвристически; это инструмент анализа, а не доказательство качества всей архитектуры. Инструменты разработки не нужны для запуска приложения.

Затем выполнен первый полный прогон на Brev: Qwen3:30b оценила все 65 диалогов. Разбор ошибок показал пропуски грубых нарушений и слабую проверку смысла цитат. На этой основе добавлены отдельные проверяемые факты, контроль ролей и независимый от черновика второй проход. После исправления нашей формулировки о достаточности исходного запроса выполнен новый единый прогон 65 диалогов. Его результаты и ограничения разобраны дальше.

Исторические документы с 1 оценённым диалогом, 24 или 49 тестами и старой палитрой описывают ранние этапы. Их нельзя использовать как актуальную сводку. Прежние экспертные оценки 65/100 и затем около 50/100 также относятся к прошлому состоянию и не являются измерением точности модели.

## Как устроено приложение

Приложение использует Python 3.10+, стандартную библиотеку, SQLite и обычные HTML/CSS/JavaScript. Для основного приложения не требуются npm-сборка и внешние Python-библиотеки. Локальный адрес — http://127.0.0.1:8765/. Арендованная модель была отдельным вычислительным сервисом, доступным через SSH; веб-приложение продолжает показывать сохранённые результаты после удаления GPU.

| Компонент | Назначение |
|---|---|
| server.py и manage.py | HTTP API, очередь задач и команды импорта, оценки и benchmark |
| cqa/domain.py и datasets.py | Проверка и нормализация данных, расчёт балла, загрузка API |
| cqa/evaluator.py и quality.py | Инструкции модели, проверка ответа, доказательств и отдельных фактов |
| cqa/proof_contracts.json | Версионированные условия проверки исходных правил |
| cqa/provider.py | HTTP-адаптеры AI-провайдеров |
| cqa/storage.py | Диалоги, снимки, версии, оценки, задачи и апелляции в SQLite |
| cqa/benchmark.py | Сопоставление предсказаний с независимым эталоном |
| static и tests | Интерфейс и автоматические проверки программы |

Рабочий процесс начинается с импорта API или собственного JSON. Сообщения получают стабильные ссылки m0001 и далее; сохраняются роли оператора, клиента, бота и системы. Пользователь выбирает диалоги и версию правил. Сервер фиксирует снимки, отправляет их модели, проверяет ответ и вычисляет итог кодом. Затем проверяющий открывает цитаты, историю, замечания и при необходимости апелляцию.

Редактор изменяет формулировки, веса, шкалы и условия N/A. Сохранение создаёт новую версию; прежние оценки не переписываются. Если импортировать изменённый диалог с тем же ID, старая оценка сохраняет прежний снимок и может быть отмечена как устаревшая. Это позволяет объяснить, какие именно данные и правила использовались в конкретном результате.

При апелляции можно подтвердить AI-ответ или заменить его допустимым ответом с причиной. Итог пересчитывается, исходная оценка сохраняется. Сейчас это функциональное разделение действий, а не настоящие серверные роли доступа.

Для Freedom Broker практическая ценность — ускорить первичную проверку операторских диалогов и показать проверяющему конкретные основания. Интеграция с Dynamics 365, корпоративные роли и промышленная обработка данных пока не реализованы. Экономия времени, качество контроля и финансовый эффект не измерялись; заявлять проценты бизнес-эффекта преждевременно.

## Данные и правила оценки

В DEV-наборе 35 русскоязычных диалогов, включая 5 голосовых транскриптов, 15 казахскоязычных и 15 англоязычных чатов. Всего 60 чатов и 5 звонков. Речь идёт о 65 диалогах, а не о 65 вопросах. В каждом оцениваются восемь критериев.

| Критерий | Вес | Ответы | Главное условие |
|---|---:|---|---|
| Контакт | 10 | yes / no | Приветствие на языке клиента и представление в первом ответе оператора |
| Потребность | 15 | yes / no / na | Недостающие сведения уточняются до рекомендации; достаточный исходный запрос даёт N/A |
| Идентификация | 20 | yes / no / na | Подтверждение личности до защищённого действия или раскрытия сведений |
| Консультация | 20 | 20 / 15 / 10 / 5 / 0 / na | Полнота и корректность существенных ответов либо правильного следующего шага |
| Эмпатия | 15 | yes / no | Вежливость и реакция на выраженное клиентом затруднение |
| Управление | 15 | 10 / 7 / 4 / 0 | Ясность, порядок, организация ожидания и отсутствие лишних переспросов |
| Завершение | 5 | yes / no / na | Итог или предложение помощи, а также прощание; учитывается возможность завершить |
| Грубая ошибка | 0 | yes / no | Оскорбление, частная платная услуга или разглашение конфиденциальных данных |

Полные формулировки и условия N/A хранятся в чек-листе; таблица — краткое изложение. Просьба сообщить данные сама по себе не доказывает успешную идентификацию. Грубая ошибка выводится отдельным флагом и не обнуляет итог автоматически. Это объясняет, почему высокий числовой балл может соседствовать с серьёзным нарушением.

Итог равен 100 × сумме произведений применимого веса на долю выполнения, делённой на сумму применимых весов. N/A исключает вес из знаменателя. Для управления максимальная ступень 10 при весе 15. Округление выполняется кодом до двух знаков; при отсутствии применимых весов итог равен null.

По тексту звонка нельзя надёжно оценить интонацию и дикцию. Исходные правила также исключают порог трёх минут для первого ответа, теги и вложения. Применение более строгих требований без изменения чек-листа исказило бы конкурсную оценку.

## Как доработан оценщик

Текущая основная версия — cqa-1.2.2-initial-request. Для исходных правил контакта, потребности, завершения и грубых ошибок модель сначала формирует отдельные факты со статусами present, absent или uncertain, объяснением и доказательствами. Сервер проверяет точность цитат, роль говорящего, границы проверенного участка и согласованность фактов с итоговым ответом.

Контакт разделён на приветствие и представление. Завершение — на возможность закончить разговор, итог или помощь и прощание. Грубые нарушения проверяются отдельно по видам. Для потребности важен порядок событий: что было известно из первоначального обращения, какие уточнения сделал оператор и когда он дал совет.

Мы исправили собственную ошибку инструкции. Формулировка «данных хватало до первой рекомендации» ошибочно включала сведения, уже полученные после уточняющих вопросов. Новая формулировка привязана к исходному запросу клиента до таких вопросов. Для звонков разрешено, что оператор сначала поздоровался, а клиент изложил вопрос позже.

Второй проход теперь получает исходный диалог без первого ответа. Это уменьшает прямое следование черновику, но оба прохода выполняет одна модель и их ошибки могут совпадать. При расхождении сервер добавляет отметку ручной проверки. Допускается одна попытка исправления невалидного результата на проход; повторно некорректный результат отклоняется.

Специальные контракты сопоставляются с точным текстом и параметрами правил, а не с ID критерия. Изменение имени, ID или веса не отключает их. Изменение текста правила, включая пунктуацию, приводит к обычной проверке без специального контракта. Это сохраняет приоритет пользовательских правил, но требует проверки сценария изменения критерия перед защитой.

Последний эксперимент использовал дополнительный адаптер Ollama source_message_enum_v9_uniform_consistency. Он ограничивал выбор цитат реальными репликами, учитывал роли и допустимые сочетания фактов завершения. Все 65 финальных результатов получены этим единым протоколом. Он сохранён в архиве воспроизводимости, но обычный путь Provider в приложении ещё не следует автоматически считать идентичным экспериментальному.

Исправлена также общая ссылка на словари внутри JSON Schema: изменение одного поля больше не меняет схему другого. Добавлены метаданные и хеши модели, инструкций, контракта, входов и адаптера; возобновление запуска проверяет факты заново. Это помогает воспроизвести эксперимент, но не доказывает правильность смысловой интерпретации цитаты.

## Что показали два полных прогона

В обоих прогонах использованы одинаковые исходные диалоги и чек-лист: хеши совпали для всех 65 пар. Модель и её digest одинаковы. Первый прогон использовал прежний протокол, второй — доработанный. При повторной проверке сначала был остановлен диагностический кандидат, затем все 65 диалогов обработаны заново одной окончательной версией. Лучшие ответы разных кандидатов не смешивались.

| Показатель | Первый прогон | Повторный прогон |
|---|---:|---:|
| Успешно оценённые диалоги | 65 / 65 | 65 / 65 |
| Контакт по нашей разметке 60 чатов | 53 / 60 | 57 / 60 |
| Пять выбранных грубых нарушений | 2 / 5 | 5 / 5 |
| Оценок 100 из 100 | 46 | 43 |
| Средний балл операторов | 89,66 | 89,97 |
| Флаг грубой ошибки yes | 2 | 5 |
| Расхождение двух проходов | 0 диалогов | 17 диалогов |
| Запросов в окончательном прогоне | 130 | 130 |
| Суммарное время запросов | 25,00 мин | 41,44 мин |

Изменились 82 из 520 ответов в 55 диалогах. По критериям: контакт — 8, потребность — 42, идентификация — 2, консультация — 6, эмпатия — 4, управление — 5, завершение — 12, грубая ошибка — 3. Большое число изменений N/A может менять знаменатель итогового балла и не всегда означает исправление ошибки.

По контакту исправлены пять из семи старых ошибок, две остались и появилась новая. Совпадение 57/60 составляет 95% именно для этого критерия на нашей разметке чатов. Это не 95% общей точности системы. Пять обнаруженных грубых нарушений — выбранные известные случаи; полнота обнаружения и ложные срабатывания на всех 65 ещё не размечены. Из шести разобранных проблем завершения исправлены пять.

Все 17 отметок неопределённости добавил сервер из-за расхождения проходов. Сама модель не сформулировала содержательных сомнений в финальных результатах. Поэтому высокий confidence не стоит трактовать как доказанную уверенность, а отсутствие отметки — как гарантию правильности.

Эти 65 DEV-диалогов уже использовались при разработке. Для честного измерения обобщения нужен новый независимый набор. Итоговую точность, MAE и долю правильных ответов относительно официального Ground Truth пока посчитать нельзя.

## Какие ошибки остаются

| Пример | Ошибка последнего прогона | Почему это важно |
|---|---|---|
| p1-kz-008 | Новый ложный contact=yes при приветствии и вопросе без представления | Точная цитата не подтверждает заявленный факт |
| p1-ru-009 | identity изменён с no на na после раскрытия сведений о счёте без проверки личности | Модель перепутала раскрытие оператором со сведениями от клиента |
| p1-ru-022 и p1-ru-029 | contact=no при явном представлении оператора | Два прежних пропуска сохранились |
| p1-ru-016 | needs=yes, хотя совет переустановить приложение дан до выяснения платформы | Нарушена последовательность уточнения и рекомендации; итог 100 завышен |
| p1-en-015 | needs=yes и максимум управления при ответе до выяснения платформы | Переспрос клиента не учтён как проблема инструкции |
| p1-kz-005 и p1-ru-014 | Максимум управления при заметных переспросах | Критерий управления оценивается слишком мягко |
| p4-ru-003 | closing=yes с доказательством без прощания оператора | Правильная роль цитаты ещё не означает правильный смысл |
| p1-en-013 и p1-kz-013 | Консультация оценена в 0 и 20 в близких сценариях | Требуется проверка согласованности RU, KZ и EN |

В голосовом p4-ru-003 ошибочность положительного завершения видна, но точный выбор no или N/A зависит от трактовки возможности закончить разговор. В p1-ru-019 применимость needs остаётся спорной: общий совет мог быть возможен до дополнительного вопроса. Такие случаи следует передать эксперту, а не превращать спорную интерпретацию в жёсткий эталон.

Остаются три основных источника риска: неверный смысл доказательства, неверное определение применимости критерия и слишком высокая уверенность в неоднозначном ответе. Схема JSON и проверка цитат защищают от части технических ошибок, но не решают эти задачи полностью.

Самый длинный вход достиг 16 105 токенов при окне 16 384. Запас для ответа мал, особенно в длинных звонках. Это основание проверить больший контекст или более компактную схему; по одним счётчикам нельзя утверждать, что конкретные данные уже были обрезаны.

## Инженерное качество и безопасность

Сервер слушает localhost. В реализации есть ограничения входного JSON, проверка Host и Origin, защитные HTTP-заголовки, экранирование динамического текста, параметризованный SQL и запрет выдачи .env и базы через статический сервер. Удалённые API используют HTTPS, редиректы запрещены. Приватным файлам назначаются ограниченные права. Это полезная база для локальной демонстрации, но не сертификация безопасности.

Исторический аудит по 27 проверкам дал 15 OK, 6 отсутствующих и 6 неприменимых пунктов. Он выполнен на ранней версии и не означает «56% безопасности». Позже исправлялись валидация чек-листа, восстановление задач и обработка ошибок. Полного нового аудита всех слоёв, инфраструктуры и зависимостей после последних изменений не проводилось.

При последней доработке прошли 72 теста. Ранее в браузере проверялись размеры 320, 390 и 1366 пикселей, черновик редактора, F5, остановка между запросами и повтор оставшихся записей. После финального импорта проверены 65/65 и отсутствие ошибок консоли. Тесты с искусственными ответами выполнялись в изолированной базе и не выдавались за результаты реальной модели.

Повторное чтение текущего кода подтвердило оставшиеся дефекты из строгого аудита:

1. При переключении карточки activeId меняется до завершения загрузки. Защита loadVersion от устаревших ответов уже есть; нужно согласованно менять видимую карточку и ID либо блокировать действия на время загрузки.
2. Завершение executor с wait=False не останавливает текущий платный запрос и может позволить worker начать следующий диалог. Нужен сигнал остановки, запрет новых вызовов после shutdown и понятный статус незавершённой операции.
3. CLI перехватывает ProviderError, но может завершаться с кодом 0 при ошибочных оценках. Автоматизация должна получать ненулевой код при провале пакета.
4. Импорт объекта с data:null может обратиться к .get у None вместо понятной ошибки 400. Нужна ранняя проверка структуры.
5. Плашка режима review читает настройку сервера, тогда как выбор карточки хранится отдельно. Отображение должно соответствовать фактическому запуску.

Для публичного сервиса дополнительно нужны аутентификация, серверные роли, лимиты запросов и расходов, аудит действий и согласованный режим обработки данных. Секреты, ранее отправленные в чат, следует заменить; факт ротации не подтверждён. В эти отчёты ключи, подписанные URL и полные транскрипты не включены.

## Что делать дальше

Первый приоритет — получить независимую экспертную разметку, особенно для идентификации, N/A, завершения и шкалы консультации. Важно сохранить отдельно набор для настройки и новые диалоги для итоговой проверки. Текущий DEV уже разобран и не подходит на роль нетронутого контрольного набора.

Второй приоритет — исправить две подтверждённые регрессии p1-kz-008 и p1-ru-009 общими правилами. Нельзя подставлять ответ по ID диалога. Нужно различать имя и приветствие, данные клиента и раскрытие оператором, запрос проверки и подтверждение проверки. Затем проверить смысл представления, помощь или итог, прощание и последовательность уточнения на разноязычных контрпримерах.

Третий приоритет — перенести проверенный экспериментальный адаптер в основной путь приложения и протестировать тот же режим через интерфейс. До этого запуск кнопкой в сайте не эквивалентен последнему эксперименту. Отдельно сравнить один проход и два на одной независимой разметке: второй проход сейчас увеличивает время и не гарантирует исправление первого.

| Шаг | Проверяемый результат готовности |
|---|---|
| Разметка и правила | Экспертные ответы с объяснениями, разрешённые спорные N/A, отдельный контроль |
| Смысловые ошибки | Снижение ошибок по каждому критерию без ухудшения критических случаев |
| Интеграция и контекст | Одинаковая конфигурация в CLI и UI; длинный звонок помещается с запасом |
| Надёжность | Исправлены пять текущих дефектов; ошибки не выглядят успешным запуском |
| Новый пилот | 3–5 разнообразных диалогов, измерены время, валидность и расходы |
| Полный прогон | Замороженная версия, хеши, полный журнал, явные пропуски и удаление GPU |
| Репетиция защиты | Новый диалог, цитата, изменение критерия и апелляция показаны за отведённое время |

На защите полезно показывать реальный процесс: загрузка нового диалога, версия правил, объяснение с переходом к реплике, флаг грубой ошибки и пересмотр. Сохранённые оценки нужно подписывать как сохранённые. Допустимость заранее рассчитанных примеров и точный сценарий изменения критерия стоит уточнить у организаторов.

Честная оценка готовности сейчас — рабочая локальная демоверсия с реальными экспериментами и заметным прогрессом, но с существенными ошибками AI. Назначать новый общий балл из 100 без Ground Truth означало бы смешать техническую готовность и неизвестную точность. Главный следующий вклад в результат хакатона даст измерение и исправление ошибок, а не новая смена цветов.
